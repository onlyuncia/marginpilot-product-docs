# Функциональные требования к MarginPilot

В таблицах описаны функции, которые работали в MarginPilot, и результат, по которому можно проверить каждую из них. Основной функционал помогает принять и применить ценовое решение; дополнительный — оценить его после продаж.

## 1. Основной функционал

| ID | Функциональное требование | Проверяемый результат |
| --- | --- | --- |
| ФТ-01 | Система получает данные, необходимые для работы с SKU, из 1С через интеграцию. | Данные из 1С доступны в расчёте выбранного SKU. |
| ФТ-02 | Система получает данные Ozon, необходимые для работы с ценами и акциями, через API. | Данные Ozon доступны при подготовке решения по SKU. |
| ФТ-03 | Система рассчитывает прогнозную экономику одной продажи SKU для рассматриваемого ценового сценария. | Менеджер видит результат расчёта до изменения цены. |
| ФТ-04 | Система сравнивает предложенную цену SKU с экономическим порогом. | Менеджер видит, какие цены не ниже порога, а какие ниже него. |
| ФТ-05 | Пока на основном экране не выбран ни один SKU, кнопка «Загрузить цены» недоступна. | Нажать кнопку можно только после выбора хотя бы одного SKU. |
| ФТ-06 | Перед отправкой цен система показывает список SKU с допустимыми и недопустимыми ценами. | Менеджер видит результаты проверки для списка товаров до передачи цен в Ozon. |
| ФТ-07 | Если среди выбранных SKU есть цена ниже экономического порога, система открывает панель предупреждения и перечисляет в ней такие артикулы. | Панель содержит только выбранные SKU с недопустимой ценой. |
| ФТ-08 | В панели предупреждения чекбоксы SKU ниже порога не отмечены по умолчанию; менеджер может отметить позиции для отправки. | Без выбора менеджера SKU ниже порога не попадают в отправляемый список. |
| ФТ-09 | Кнопка «Отмена» закрывает панель предупреждения и отменяет отправку пакета. | Ни одна цена из текущего списка не передаётся в Ozon. |
| ФТ-10 | При нажатии «Подтвердить» система формирует пакет из SKU с допустимой ценой и вручную отмеченных SKU ниже порога. | Неотмеченные SKU ниже порога не входят в отправляемый пакет. |
| ФТ-11 | Если при нажатии «Подтвердить» список для отправки пуст, система показывает toast-уведомление «SKU не выбраны». | Запрос на изменение цен в Ozon не выполняется. |
| ФТ-12 | После предупреждения система сохраняет отправленный пакет с пользователем и временем, а для вручную включённых SKU ниже порога — отдельное решение. | Можно установить, кто продолжил отправку и какие исключения подтвердил. |
| ФТ-13 | При отсутствии цен ниже порога система отправляет пакет после нажатия «Загрузить цены»; при их наличии — после нажатия «Подтвердить», если пакет не пуст. | Цены передаются в Ozon через API только после соответствующего действия менеджера. |
| ФТ-14 | Система разбирает ответ Ozon на отправку цен по каждому SKU: признак `updated` и список `errors`. | Менеджер видит, какие позиции Ozon сообщил как обновлённые, а по каким вернул ошибку. |
| ФТ-15 | После отправки система автоматически получает актуальные цены из Ozon и сверяет их с отправленными. | Результат применения проверяется отдельно от ответа на запрос об изменении цены; ручной запуск сверки не требуется. |
| ФТ-16 | При недоступности Ozon API система показывает toast-уведомление. | Менеджер видит, что применение цен не подтверждено. |
| ФТ-17 | При таймауте ответа на отправку система сохраняет пакет со статусом «Результат отправки не подтверждён», показывает toast-уведомление и сверяет актуальные цены по SKU. Для непроверенных SKU чтение повторяется позже. | Показан toast с заголовком «Нет ответа от Ozon» и сообщением из [UC-001 (А5)](10-USE-CASES.md). Менеджер видит, где цена совпала с отправленной, где не совпала и где проверку пока не удалось выполнить. |
| ФТ-18 | Пока результат отправки после таймаута не выяснен, система не отправляет пакет повторно автоматически. | Таймаут сам по себе не запускает второй запрос на изменение тех же цен. |
| ФТ-19 | Система позволяет управлять участием SKU в акциях Ozon через API. | Согласованное действие по участию товара передаётся в Ozon. |
| ФТ-20 | После отправки действия по акции система автоматически получает актуальный статус участия выбранных SKU и сверяет его с целевым, в том числе после таймаута ответа Ozon. Если статус получить не удалось, чтение повторяется позже. | По каждому SKU показано, подтверждён ли целевой статус или результат остаётся невыясненным. |
| ФТ-21 | Пока отправка действия по SKU и акции не завершена или её результат не подтверждён, система не передаёт в Ozon повторный запрос на то же действие по этому товару. | Повторное нажатие не создаёт дублирующего запроса; после установления результата действие можно повторить только для SKU, у которых целевой статус не достигнут. |

ФТ-07–ФТ-12 описывают предупреждение, а не блокировку: менеджер мог отправить цену ниже порога, и система сохраняла его решение в журнале.

## 2. Дополнительный функционал

| ID | Функциональное требование | Проверяемый результат |
| --- | --- | --- |
| ФТ-22 | Система получает фактические рекламные расходы для анализа экономики товара. | Расходы доступны для сопоставления с плановым расчётом. |
| ФТ-23 | После подтверждённого применения цены или изменения участия в акции система сохраняет новую версию планового расчёта SKU, не перезаписывая прежние. | Для продажи можно определить план, действовавший на момент её совершения. |
| ФТ-24 | Система сопоставляет плановую и фактическую экономику SKU за выбранный период — в сумме и в пересчёте на проданную единицу. Отклонение рассчитывается как `факт − план`. | План за период учитывает фактически проданное количество по каждой действовавшей версии расчёта. При отсутствии продаж расходы остаются видны, а показатели на проданную единицу не рассчитываются. |

Плановые рекламные затраты и фактические списания учитывались отдельно. Положительное отклонение прибыли означает результат выше плана, положительное отклонение расходов — перерасход.
